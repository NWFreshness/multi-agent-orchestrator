# Feature 2.4: `output_schema` content enforcement

**Phase:** 2 — Model selection & overrides
**Status:** in_progress (spec author running)
**Estimated effort:** half-day wall
**Depends on:** 1.6 (synthesis contract; F1.6 references the per-specialist
`output_schema` field and gap rule (a))
**Blocks:** 2.5 (cost abort reuses the validation surface)

## Goal

Per-specialist `output_schema` validated against a real JSON Schema BEFORE
dispatch (currently the F1.4 validator only checks that the value is a
dict). A specialist that returns output not matching its declared schema
is recorded as `status: failed` in the dispatch trace, which the F1.6
synthesis contract already surfaces in `gaps` (rule a: every failed
specialist MUST appear in gaps).

## Scope

Include:
- `scripts/validate_schema.py` (new, stdlib-only). Exposes:
  - `validate_against_schema(value: Any, schema: dict) -> Tuple[bool, Optional[str]]`
    — returns `(True, None)` if `value` matches `schema` per a stdlib-only
    JSON-Schema subset, or `(False, "path: <reason>")` otherwise.
  - `check_plan_schemas(plan: dict) -> List[str]` — iterates the plan's
    `specialists[]`, returns a list of validation error strings (empty
    list = all schemas are well-formed AND each specialist's
    `output_schema` is a non-empty JSON Schema object). Use this in
    `validate_plan.py`'s E3 (per-specialist fields) to add a sub-rule:
    `output_schema` must be a valid JSON Schema subset.
  - `--self-test` flag with a built-in fixture suite (~8–10 cases
    covering primitive types, nested objects, arrays, required fields,
    enum, oneOf, $ref, malformed schema, malformed value, etc.).
- **JSON Schema subset (locked)**: type, properties, required, items,
  additionalProperties, enum, const, anyOf, oneOf, allOf, $ref (with a
  flat $defs block at the schema root), minimum, maximum, minLength,
  maxLength, pattern. NOTHING ELSE. If a specialist supplies a schema
  with a key outside this subset, `check_plan_schemas` reports it as
  an E3 error (not a crash). Phase 2 users can read the spec; Phase 3
  may extend the subset.
- **Integration with F1.4** (scripts/validate_plan.py):
  - E3 sub-rule added: `output_schema` must be (a) a non-empty dict and
    (b) every key must be in the locked subset above. Phase 1's "must
    be a dict" check stays; this adds the keys-allowed check.
  - E8 (nesting guard) gets a sub-rule: nested schemas inside a
    specialist's `output_schema` count toward the 64-depth cap.
  - All other E-rules unchanged. The 15 F1.4 self-test fixtures stay
    green.
- **Integration with F1.5** (scripts/dispatch.py):
  - After dispatch, before trace write: for each specialist, parse the
    `output_path` (a `logs/specialists/<id>.<n>.json` per F1.5) and
    re-validate the `output` field against the per-specialist
    `output_schema`. If the validation fails, the record is marked
    `status: failed` (the existing F1.5 trace path supports this) with
    an `error: output_schema mismatch: <reason>` field. Successful
    specialist records gain a new optional `schema_ok: true` field.
  - Default: schema validation is ON. Add `--no-schema-check` flag
    (default False) for the rare case where a user wants raw output.
- **Integration with F1.6** (references/synthesis.md):
  - The synthesis contract's gap rule (a) — "every `failed_specialist`
    MUST appear in `gaps`" — now extends to include schema-mismatch
    failures. The synthesis input shape's per-specialist entry gains an
    optional `failure_reason` field that the dispatcher populates with
    either the retry error (F1.7) or the schema mismatch reason.
- `SKILL.md` §4 Validate paragraph: ONE appended clause
  `Specialist outputs are validated against their declared output_schema
  before trace write; mismatches surface in the orchestration log as
  failed specialists (per F1.6 gap rule a).`
- `README.md` status table: F2.4 → In progress; per-feature status flip.
- `docs/specs/phase-2/2.4-output-schema-enforcement.md` Status → completed.

## Locked JSON Schema subset (restate)

The validator supports: `type`, `properties`, `required`, `items`,
`additionalProperties`, `enum`, `const`, `anyOf`, `oneOf`, `allOf`, `$ref`
(with `$defs` at root), `minimum`, `maximum`, `minLength`, `maxLength`,
`pattern`. Recursion via `properties` → nested `properties` is
supported, subject to the existing MAX_NESTING_DEPTH (64) cap.

## Implementation notes

- Decision D29 (controller-locked): the JSON Schema subset is FROZEN
  for Phase 2. Adding keywords (e.g. `$dynamicRef`, prefixItems) is
  Phase 3 work. The implementer MUST NOT silently support keywords
  outside the locked subset — flag them as E3 errors at plan-validation
  time, not as a runtime crash.
- Decision D30: post-dispatch schema check is FAIL-FAST PER
  SPECIALIST. A failed schema check does NOT cancel the rest of the
  trace (each specialist's check is independent). The dispatcher
  classifies it as `status: failed` for that specialist, with the
  `failure_reason` propagated to the F1.6 synthesis layer.
- Gotcha: the stub's output JSON content is whatever the F1.5 stub
  writes — it includes `id`, `role`, `task`, `context`, `output_schema`
  (echoed back), `timestamp`, `stub: true`. If the specialist's declared
  `output_schema` is `{ "type": "object", "required": ["answer"],
  "properties": { "answer": { "type": "string" } } }`, the stub output
  FAILS schema validation (no `answer` field). The check is REAL —
  the test rig should be set up to use a per-specialist output that
  matches a known schema, then the F1.5 stub's actual output should be
  expected to FAIL. The implementer may need a test fixture where the
  stub writes a custom payload (via a sentinel env var, similar to
  F1.7's `retry_test_overrides`).
- Gotcha: $ref resolution is at root only (`$defs`). Cross-file $ref is
  out of scope; flag unsupported keywords.
- Reference: references/synthesis.md §4 (gap rule a); PRD §6 (R6
  nesting); scripts/validate_plan.py (E3 and E8 sub-rules); F1.5 trace
  format.
