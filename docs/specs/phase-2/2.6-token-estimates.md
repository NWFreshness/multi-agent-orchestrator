# Feature 2.6: Per-call token estimate surfaced in log

**Phase:** 2 — Model selection & overrides
**Status:** in_progress (spec author running)
**Estimated effort:** half-day wall
**Depends on:** nothing (independent of F2.5; F2.6 reads the F2.5 cost
configuration but doesn't share code paths with the abort logic)
**Blocks:** nothing (Phase 2 final feature)

## Goal

Each per-specialist trace record carries a `token_estimate: int` field
(0 by default; set by an internal per-call token model), and
`scripts/write_log.py`'s per-specialist H3 sections surface that
estimate alongside `elapsed_ms`. The goal is observability — the user
sees how many tokens a specialist call used, even though the stub
returns deterministic content in Phase 1/2.

## Scope

Include:
- **Trace format extension** (`scripts/dispatch.py`):
  - Each per-specialist trace record (the `record` dict written to
    `logs/orchestration-trace.jsonl`) gains an optional
    `token_estimate: int` field. Default value: 0 (no estimate).
  - F1.5's stub `scripts/run_specialist.py` writes a deterministic
    JSON file per F1.5. The dispatcher reads the file's `task` and
    `context` field lengths to compute a Phase 2 token estimate:
    `token_estimate = max(1, (len(task) + len(context)) // 4)` (the
    well-known 4-chars-per-token approximation; this is a STUB and
    Phase 3 will replace with a real provider estimate).
  - The estimate is COMPUTED BY THE DISPATCHER (not by the stub),
    so F1.5's stub stays untouched.
- **`--tokens-per-char N` flag** (`scripts/dispatch.py`):
  - Default 0.25 (the inverse of 4 chars/token). Lets a user override
    the approximation: `--tokens-per-char 0.5` doubles the estimate
    (2 chars/token, a tight code-y model).
  - Order-independent.
- **Log writer extension** (`scripts/write_log.py`):
  - The per-specialist attempt row now includes `tokens=N` when the
    trace record has a non-zero `token_estimate`. When zero (the
    default), the `tokens=` part is omitted (don't print a noisy
    "tokens=0" line).
  - Per-specialist aggregate at the bottom of the log gains a
    `Total estimated tokens: N` line, summing across final records.
- **Self-test extensions**:
  - `scripts/dispatch.py` --self-test: 2+ new fixtures (one with
    `--tokens-per-char` default, one with override; both verify the
    trace record's `token_estimate` and the log writer's output).
  - `scripts/write_log.py` --self-test: 1+ new fixture exercising
    the new `tokens=` and `Total estimated tokens:` rendering.
  - `scripts/run_tests.py`: bump dispatch 13→15, write_log 7→8, EXPECTED_TOTAL 36→39.
- `SKILL.md` §4 Validate paragraph: ONE appended clause
  `Token estimate is computed per-specialist (≈ chars/4 by default;
  override with --tokens-per-char N) and surfaced in the
  orchestration log alongside elapsed_ms.`
- `README.md` status table: F2.5 → Done, F2.6 → In progress.
- `docs/specs/phase-2/2.6-token-estimates.md` Status → completed.

## Exclude (for now)

- Real provider-side token counting. The 4-chars-per-token
  approximation is a stub; Phase 3 will replace with a real estimate.
- Per-role token multipliers (uniform approximation in Phase 2).
- Persistent token history (separate concern).
- Changing the F1.5 stub to report tokens. The dispatcher computes
  the estimate from the stub's `task` and `context` field lengths.

## Locked behavior

- The estimate is computed AS `max(1, (len(task) + len(context)) *
  tokens_per_char)`, cast to int. If `tokens_per_char == 0`, the
  estimate is 0 (effectively disabled, but the field is still
  present so downstream readers can rely on its existence).
- The estimate appears in the trace record as `token_estimate: int`.
  Default value when disabled: 0.
- The log writer's per-attempt row format becomes:
  `- Attempt N: <status>, elapsed=<ms>ms, output=<path>,
  retries=<int>` and conditionally `, tokens=<int>` when
  `token_estimate > 0`.
- The aggregate section gains `Total estimated tokens: N` (sum of
  final records' `token_estimate` values).

## Implementation notes

- Decision D35 (controller-locked): the estimate is computed BY THE
  DISPATCHER, not by the stub. The stub stays untouched (F1.5 contract
  holds). The dispatcher reads `task` and `context` from the JSON the
  stub wrote and computes the estimate from those string lengths.
- Decision D36: `tokens_per_char = 0.25` is the default (4 chars
  per token, the standard approximation for English text). User
  override via `--tokens-per-char N`.
- Decision D37: the trace's `token_estimate` field is INT (rounded
  down from the float computation). Negative or zero inputs are
  floored to 0; max(1, ...) gives a minimum of 1 when
  `tokens_per_char > 0` AND any text exists.
- Gotcha: the dispatcher already reads the stub's JSON to apply the
  F2.4 post-dispatch schema check (`_read_specialist_output` in
  dispatch.py). Add the token estimate computation to the same
  function so it's computed once per specialist per final record,
  not separately.
- Gotcha: when a specialist's stub output has empty `task` and
  empty `context` (pathological), the estimate is 0. Don't crash.
- Gotcha: the log writer's per-attempt row is a single line. If
  adding `tokens=N` makes the line too long, the lock is "wrap
  with a backslash continuation" or "use a multi-line bullet
  format". Read the existing format and pick the cleanest extension
  that doesn't break the locked shape.
- Reference: PRD §10 (success metrics mention cost as one of them);
  scripts/write_log.py (per-specialist H3 attempt format, locked
  in F1.8 spec); F1.5 trace format (the field is additive, doesn't
  break F1.5).
