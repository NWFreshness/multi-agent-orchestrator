## Goal

Codify, in one place, the resolution chain that turns "the user wants the
Orchestrator on model X" into a concrete model string the dispatcher can
hand to `delegate_task` — and apply the same chain to the subagent default,
independently (independence is F2.2's contract; F2.1 documents the chain).

## Scope

Include:

  1. **Overview** — one paragraph: Phase 1 hard-coded the models; Phase 2 lets

  2. **The two resolution targets** — explicitly: the Orchestrator model

  3. **Resolution chain — locked 4-tier precedence, first match wins**:
     | # | Tier | Source | Variable / key | Notes |
     | - | ---- | ------ | -------------- | ----- |
     | 1 | options | explicit skill option or CLI flag | `orchestrator_model` / `subagent_model` (TBD in F2.5 CLI; for F2.1 the doc names the canonical key) | Highest priority. If set, lower tiers are ignored for that target. |

     **First-match-wins rule (D22):** for a given target, walk tiers 1→4; the
     first non-empty value wins. The other target is unaffected.
  4. **Per-tier examples** — one worked example per tier showing input and
     resolved output. Each example MUST end with the explicit literal
     `resolved: <value>` so a controller grep proves the chain.
  5. **The single resolution helper** — `resolve_model(target: str) -> str`
     importable from the script tree (path TBD by F2.5 — F2.1 names the

     or `"subagent"`. Returns the resolved model string. Same chain, both
     targets, with independence enforced inside (one `resolve_model` call MUST

  6. **Empty / unset semantics** — empty string from env or config tier is

  7. **Error posture** — none in F2.1. Resolution NEVER raises. An invalid

     detect later (when `delegate_task` rejects it). F2.1 deliberately

  8. **What this is NOT** — out of scope: any UI for selection (PRD §6

## Spec section

### Locked resolution chain (D22, first match wins)

```
resolve_model(target) :=                        # target ∈ {"orchestrator","subagent"}
  if options[target]                       != ""  return options[target]
  if env["HERMES_<TARGET>_MODEL"]          != ""  return env["HERMES_<TARGET>_MODEL"]
  if config["skills.multi_agent_orchestrator.<target>_model"] != ""
                                              return config[...]   # F2.3 pins the path
  return PHASE1_DEFAULT[target]                  # floor — never absent
```

Where `PHASE1_DEFAULT["orchestrator"] = "opencode-go/kimi-k3"` and
`PHASE1_DEFAULT["subagent"]   = "opencode-go/deepseek-v4.1-flash"`. Tier 1
(`options`) is the only tier whose variable name F2.1 leaves TBD for the
implementer to settle — the canonical env var names (`HERMES_ORCHESTRATOR_MODEL`,
`HERMES_SUBAGENT_MODEL`) are LOCKED (D22) and MUST appear in the doc.

### Worked example per tier (one of each — doc MUST contain all four)

```text
# Tier 1 — explicit option
options = {"orchestrator_model": "minimax/MiniMax-M3"}
→ resolve_model("orchestrator") = "minimax/MiniMax-M3"
  resolved: minimax/MiniMax-M3

# Tier 2 — env var
HERMES_ORCHESTRATOR_MODEL=opencode-go/minimax-m3
→ resolve_model("orchestrator") = "opencode-go/minimax-m3"
  resolved: opencode-go/minimax-m3

# Tier 3 — per-profile config
# ~/.hermes/config.yaml:
#   skills:
#     multi_agent_orchestrator:
#       orchestrator_model: opencode-go/minimax-m3
→ resolve_model("orchestrator") = "opencode-go/minimax-m3"
  resolved: opencode-go/minimax-m3

# Tier 4 — Phase 1 default floor
(no override anywhere)
→ resolve_model("orchestrator") = "opencode-go/kimi-k3"
  resolved: opencode-go/kimi-k3
```

A symmetric set for `target="subagent"` (floor `opencode-go/deepseek-v4.1-flash`)
MUST also appear — controller grep proves both floors are present.

## Implementation notes

- Decision D20 (controller-locked, do not relitigate): Phase 1 default stays
  the floor — a user who has configured nothing gets the same models Phase 1
  shipped. No surprise upgrade.
- Decision D22 (controller-locked): the 4-tier chain (options > env > config
  > default), first match wins, single resolution helper exposed for import.
  F2.1 is the doc that codifies this; F2.5 writes the helper.
- Decision D23 (controller-locked): no UI for selection in Phase 2.
  Resolution is by env var / config / option only. Doc MUST NOT mention a
  TUI / interactive picker.
- Decision D24 (controller-locked): still stdlib-only at the script boundary.
  F2.1 itself is a doc; F2.5's helper import (when it ships) must be stdlib.
- Decision D25 (controller-locked): F2.1 mirrors Phase 1 format. This spec
  is the format reference.
- Gotcha: tier 1's exact variable name is intentionally left flexible for
  F2.5 to pin. F2.1 names the precedence + semantics; F2.5 names the keys.
  The doc MUST use the words `option` / `options` (not the bare word `flag`
  — F2.5 may use either depending on entry point).
- Gotcha: independence (D21) is documented here as a forward-pointer to
  F2.2; F2.1 only says "the chain applies to one target at a time" and
  defers the explicit three-case worked example to F2.2.
- Reference: PRD §§6 (R11), 9 (Phase 2 list), 14 (decisions D20–D22);
  `references/orchestrator.md` §§3 (specialist `model` field default),
  6 (re-invocation — same model every dispatch).
