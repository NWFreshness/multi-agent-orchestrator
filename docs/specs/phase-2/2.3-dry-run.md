# Feature 2.3: `--dry-run` plan preview

**Phase:** 2 — Model selection & overrides
**Status:** completed
**Estimated effort:** half-day wall (spec; implementation gated on F2.5 for the model-resolution part)
**Depends on:** 2.1 (resolution contract; PR #11)
**Blocks:** 2.4 (output_schema enforcement reuses the dry-run surface to show the user the schema it's enforcing against)

## Goal

A `--dry-run` flag (or plan-preview command) that runs the full Phase 1 plan
contract (validate → resolve-model) but stops before any dispatch, and
prints what *would* happen if the user ran the command for real. The user
sees: (a) the validated plan, (b) the resolved Orchestrator + subagent
models, (c) the synthesized plan summary (specialists + batch layout),
(d) any warnings (unknown role, non-default model override), and exits 0.

## Scope

Include:
- A new `scripts/plan_preview.py` (stdlib-only) that takes a plan JSON path
  and prints the locked preview shape below. Re-uses
  `scripts/validate_plan.validate(plan)` (F1.4 importable) and
  `scripts/run_specialist.run_specialist` is NOT touched (no specialist
  dispatch).
- A `--dry-run` flag added to `scripts/dispatch.py` (F1.5 + F1.7) that
  calls `plan_preview.print_preview(plan, resolved_models, warnings)` and
  exits 0 without dispatching. The flag is read-only: it does not write
  the trace, does not spawn any specialist, does not increment any
  counters. It does validate, resolve, and print.
- The resolved-models step calls `resolve_model("orchestrator")` and
  `resolve_model("subagent")` from `references/model-resolution.md` (F2.1
  contract; Python implementation arrives in F2.5). In F2.3's PR the
  resolution call is a thin stub: read env var + fall back to Phase 1
  default. F2.5 replaces the stub with the full 4-tier chain. The PUBLIC
  contract of `resolve_model(target)` does not change between F2.3 and
  F2.5 — only the implementation behind it.
- `SKILL.md` §4 Validate paragraph: ONE appended clause `Add --dry-run to
  scripts/dispatch.py to print the plan + resolved models without
  dispatching (exit 0).` (frontmatter byte-identical, 8 sections intact).
- `README.md` status table: F2.3 → In progress; per-feature status flip.
- `docs/specs/phase-2/2.3-dry-run.md` Status → completed.

## Locked preview shape (markdown)

```markdown
# Plan preview

- Plan: <absolute path or "-">
- Validated: yes (15/15 expected checks)
- Orchestrator model: opencode-go/kimi-k3 (source: <which tier>)
- Subagent model:   opencode-go/deepseek-v4.1-flash (source: <which tier>)
- Specialists: <N> (target ~10, range 3–15)
- Batches: <B>
- Warnings: <count>
  - <each warning on its own line, prefixed with "  - ">

## Specialists (preview)

| id  | role        | goal (truncated to 60 chars) | model (resolved)        |
|-----|-------------|------------------------------|-------------------------|
| r1  | researcher  | gather X ...                 | opencode-go/deepseek-... |
| ... | ...         | ...                          | ...                     |

## Batch layout

- Batch 0: r1, cr  (parallel)
- Batch 1: wr      (depends on r1)

## Next step

Remove --dry-run to dispatch. Use scripts/validate_plan.py for plan
validation only, or scripts/dispatch.py --dry-run for the full preview.
```

Tier source is one of: `option`, `env`, `config`, `default`. The default
column is the F2.1 floor model.

## Implementation notes

- Decision D26 (controller-locked): the dry-run's `resolve_model` call in
  F2.3 is a THIN STUB — env var + default floor. F2.5 replaces the body.
  The signature is locked: `resolve_model(target: str) -> str` returning
  the model string with the tier as a side-channel (tuple or named
  return). F2.3 uses a tuple return so F2.5 doesn't have to change the
  caller when it adds config and option support.
- Decision D27: the dry-run does NOT validate the model string (e.g.
  "does opencode-go/alt exist?"). That's an integration concern and
  lives in F2.5 with the rest of the resolution chain. F2.3 prints the
  raw string the user gave.
- Decision D28: warnings (non-blocking) include (a) unknown role in
  `archetypes.md`, (b) any specialist whose `model` field in the plan
  differs from the resolved default (i.e. the plan's per-specialist
  model field is present but not equal to the resolved model), (c)
  batch layout with cycles (the validator already blocks cycles; the
  dry-run prints a warning if a cycle is present in the plan's
  dependencies, even if the validator passed — defensive).
- Gotcha: the preview MUST NOT spawn anything. Add an early `return`
  after `print_preview(...)` in dispatch.py when `--dry-run` is set; do
  NOT enter the dispatch loop.
- Gotcha: `--dry-run` and the existing `--self-test` flags must not
  conflict. `--self-test` is a no-plan flag; `--dry-run` requires a
  PLAN.json. argparse conflict is acceptable (argparse will reject
  `--self-test PLAN.json` per the F1.5 self-test path).
- Reference: PRD §§6 (R3, R13, R15), 8; references/orchestrator.md
  (re-invocation pattern); references/synthesis.md (synthesis contract
  for the preview's tone); F2.1 (resolution contract); F2.2
  (independence rule).
