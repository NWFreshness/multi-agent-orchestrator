## Spec section

### The independence rule (D21)

```
Orchestrator tier values   ┐
                            │  two disjoint chains
Subagent tier values       ┘

resolve_model("orchestrator")   reads Orchestrator tiers only.
resolve_model("subagent")       reads subagent tiers only.
```

`HERMES_ORCHESTRATOR_MODEL` does not touch the subagent default.
`HERMES_SUBAGENT_MODEL` does not touch the Orchestrator default. The
options and config tiers obey the same separation.

### Three worked cases (doc MUST contain all three)

```text
# Case A — override only the Orchestrator
env = { HERMES_ORCHESTRATOR_MODEL: "minimax/MiniMax-M3" }   # HERMES_SUBAGENT_MODEL unset
config = {}                                                 # no per-profile overrides
options = {}
→ resolve_model("orchestrator") = "minimax/MiniMax-M3"
  resolved orchestrator: minimax/MiniMax-M3
→ resolve_model("subagent")     = "opencode-go/deepseek-v4.1-flash"
  resolved subagent:     opencode-go/deepseek-v4.1-flash

# Case B — override only the subagent
env = { HERMES_SUBAGENT_MODEL: "opencode-go/minimax-m3" }    # HERMES_ORCHESTRATOR_MODEL unset
config = {}
options = {}
→ resolve_model("orchestrator") = "opencode-go/kimi-k3"
  resolved orchestrator: opencode-go/kimi-k3
→ resolve_model("subagent")     = "opencode-go/minimax-m3"
  resolved subagent:     opencode-go/minimax-m3

# Case C — override both
env = { HERMES_ORCHESTRATOR_MODEL: "minimax/MiniMax-M3",
        HERMES_SUBAGENT_MODEL:     "opencode-go/minimax-m3" }
config = {}
options = {}
→ resolve_model("orchestrator") = "minimax/MiniMax-M3"
  resolved orchestrator: minimax/MiniMax-M3
→ resolve_model("subagent")     = "opencode-go/minimax-m3"
  resolved subagent:     opencode-go/minimax-m3
```

Doc MUST contain one line per case starting with `resolved orchestrator:` and
one with `resolved subagent:` (controller grep proves both targets per case).
Six `resolved …:` markers total (three cases × two targets) is the strict
target.

## Implementation notes

- Decision D21 (controller-locked, do not relitigate): Orchestrator and
  subagent model overrides are independent. Two resolution chains; one
  `resolve_model` call per target. Cross-talk is a defect.
- Decision D22 (controller-locked): the 4-tier chain (options > env > config
  > default) is identical for both targets. F2.2 adds independence, not new
  tiers.
- Gotcha: section placement — pick the cleaner spot. Two viable options:
  (a) after F2.1 §3 (resolution chain) and before §4 (per-tier examples) —
    reads as "first the chain, then the per-target rule, then the worked
    single-target examples";
  (b) after §5 (`resolve_model` helper) and before §6 (empty semantics) —
    reads as "here is the helper, here is how it's called for both targets,
    here are the edges".
  Both are acceptable. The implementer MAY pick either; the controller's
  grep only checks the section is titled `Independent overrides (D21)` and
  the six `resolved …:` markers are present.
- Gotcha: the `resolved orchestrator:` / `resolved subagent:` markers must
  appear EXACTLY 6 times in the new section (one pair per case). F2.1's
  per-tier `resolved:` markers (which use a different prefix) must NOT be
  renamed — the controller grep uses prefix to avoid double-counting.
- Gotcha: do not edit F2.1's §3 table to add a "target" column. The table
  is target-agnostic by design; F2.2 adds a per-target worked-example
  block. Editing F2.1's table would conflate the two specs.
- Reference: PRD §6 (R11 — explicit independence language), §9 Phase 2 list,
  §14 (D21); `references/model-resolution.md` §3 (the chain F2.2 re-uses
  per-target), §5 (the helper F2.5 will import); `references/orchestrator.md`
  §§2–3 (specialist `model` is the subagent-tier value).
