# Feature 1.8: Orchestration log writer

**Phase:** 1 — MVP, fixed models
**Status:** in_progress
**Estimated effort:** half-day wall (subagent implement + two-stage review)
**Depends on:** 1.5, 1.6
**Blocks:** 1.9

## Goal

A stdlib-only CLI that reads the dispatcher's trace (`logs/orchestration-trace.jsonl`,
F1.5/F1.7 format) and writes the human-readable per-Run orchestration log
required by PRD R9 — the file the user can read to see roles, prompts,
status, timing, and (in F1.10) the synthesized answer.

## Scope

Include:
- `scripts/write_log.py` — stdlib-only CLI.
  - CLI: `python3 scripts/write_log.py --trace PATH --out DIR
    [--task-summary TEXT] [--workspace PATH]`. Reads the trace, writes
    `<out>/orchestration-log-<UTC-timestamp>.md` per PRD R9 convention.
  - Default `--trace` = `logs/orchestration-trace.jsonl`; default `--out` = current dir;
    default `--workspace` = current dir. argparse with all three.
  - Timestamp format: `YYYYMMDDTHHMMSSZ` (UTC, sortable, no colons — safe in
    any filename).
  - `--self-test`: writes a deterministic log from a fixture trace under
    `logs/orchestration-trace.jsonl`, asserts the output file exists, has a
    sensible shape, and contains the locked required sections.
- Log file shape (locked; referenced by F1.10 tests):
  1. Header — `# Orchestration Log` + run timestamp + `--task-summary` if
     provided + workspace path.
  2. **Plan summary** — count of specialists, batch count, plan id (if
     present in trace).
  3. **Per-specialist sections** — one H3 per unique specialist id in the
     trace, in first-encounter order. For each:
     - role, goal (from input — but F1.5 doesn't carry goal in the trace, so
       leave it as a TODO slot for F1.10, or omit if absent), all attempts
       chronologically: timestamp, status, retries, elapsed_ms, output_path,
       error (if any). One subsection per attempt.
  4. **Aggregate stats** — total elapsed (sum of elapsed_ms across final
     lines), success count, failure count, retry count.
  5. **Synthesis placeholder** — a section titled "Synthesis" with a literal
     `[Awaiting F1.6 synthesizer output]` placeholder. F1.10 will inject
     real content. This is intentional — the log writer does NOT synthesize.
- **No re-derivation**: log writer reads the trace as-is. Doesn't recompute
  timing, doesn't validate, doesn't summarize intent — it formats what's on
  disk.
- `SKILL.md` §6 Observability: ONE appended clause `Run scripts/write_log.py
  (default paths) to produce the per-Run orchestration log at
  orchestration-log-<UTC-timestamp>.md.`
- `README.md` status table: F1.8 → In progress.

Exclude (for now):
- Real synthesis (F1.6's job; placeholder is fine).
- Token / cost estimates (PRD R9 mentions "token/cost estimate" but the stub
  doesn't track these; the log will show a `[token estimate: n/a]` line
  per specialist to make the gap explicit. F1.10 or a later phase can fill
  this in).
- Streaming / live updates (Phase 3 PRD F3.4).
- New files beyond `scripts/write_log.py` (and the log file it produces,
  which is gitignored).
- No changes to F1.4/F1.5/F1.6/F1.7 contracts.

## Spec section

Locked output template (sections 1–5 in order, locked headings):

```markdown
# Orchestration Log

- Run timestamp (UTC): 20261009T201500Z
- Task summary: compare top 5 ORMs for Node.js 2026
- Workspace: /Users/tylermayfield/Documents/projects/...

## Plan

- 6 specialists
- 2 batches

## Specialists

### r1 (researcher)

- Attempt 1: ok, elapsed=142ms, output=logs/specialists/r1.1.json, retries=0
- Attempt 2: ok, elapsed=140ms, output=logs/specialists/r1.2.json, retries=1

### a2 (critic)
... (one H3 per unique specialist id, in first-encounter order; one row per attempt chronologically)

## Aggregate

- Total elapsed: 850ms
- Succeeded: 6
- Failed: 0
- Retried: 2

## Synthesis

[Awaiting F1.6 synthesizer output]
```

The `error` field is included only when present in the trace line.

## Implementation notes

- Decision D15 (controller-locked): the log writer is a FORMATTER, not an
  analyzer. It reads the trace and produces a markdown file. No re-derivation.
- Decision D16: F1.5's trace doesn't include the specialist's goal/context
  in each line — only `id`, `role`, and runtime fields. The log writer
  therefore can only show what the trace has. If goal is needed in the log
  output, that's a F1.5 trace-extension request, NOT a F1.8 scope creep.
  (The spec is explicit: omit goal if absent, no TODO line.)
- Gotcha: multiple trace lines per specialist (F1.7 history). The log must
  show ALL attempts in order, with `retries` as the cross-reference to the
  schema. Don't dedup; don't pick the final record.
- Gotcha: timestamp from `datetime.now(timezone.utc)`, formatted as
  `strftime("%Y%m%dT%H%M%SZ")`. Filename uses the same.
- Reference: PRD R9 (logging requirements), references/synthesis.md §5
  (synthesis placeholder pattern), F1.5 trace format, F1.7 retries field.
