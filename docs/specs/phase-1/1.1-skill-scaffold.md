## Spec section

Frontmatter (exact — the description head is pinned byte-for-byte):

```yaml
---
name: multi-agent-orchestrator
description: Use when a task needs multiple specialized subagents — spawns an Orchestrator that selects ~10 specialists, dispatches them in parallel via delegate_task, and returns a synthesized answer.
version: 0.1.0
metadata:
  hermes:
    tags: [orchestration, multi-agent, delegation, synthesis, parallel]
    related_skills: [subagent-driven-development, dispatching-parallel-agents, hermes-agent]
---
```

Description-head rule: the first 57 characters must be a self-contained trigger.
Pinned head is `Use when a task needs multiple specialized subagents` (52 chars).
The implementer MUST keep this head byte-identical; only text after the em-dash
may be edited.

Body sections (all 8, concise, implementation-oriented):
1. Overview (3–5 sentences; what the skill does).
2. When to Use (trigger conditions + explicit non-triggers, e.g. single-domain
   tasks short-circuit per PRD R15).
3. Phase 1 pinned models (Orchestrator `opencode-go/kimi-k3`, subagents
   `opencode-go/deepseek-v4.1-flash`; no user overrides in Phase 1).
4. The Loop (short-circuit → spawn Orchestrator → plan → validate → batch
   dispatch → recover → synthesize → log; one paragraph per step, ref PRD §8).
5. Delegation contract (`delegate_task` arrays per batch; per-specialist
   goal/context/output_schema; `max_spawn_depth = 2`; 3–15 specialists, target ~10).
6. Observability (log path convention `<workspace>/orchestration-log-<timestamp>.md`).
7. Safety (no privilege escalation; specialists get reduced toolsets unless the
   parent session grants more).
8. References index listing `references/archetypes.md`, `references/output-schema.md`,
   `references/orchestration-log.md` as forward refs marked "defined in F1.3 / F1.6 / F1.8".
