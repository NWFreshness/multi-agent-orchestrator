# Feature 1.5: Batch dispatch (no real LLM, deterministic stub)

**Phase:** 1 — MVP, fixed models
**Status:** completed
**Estimated effort:** half-day wall (subagent implement + two-stage review)
**Depends on:** 1.4
**Blocks:** 1.6, 1.7, 1.8

## Goal

Two stdlib-only CLI scripts that together turn a validated plan into a
per-specialist trace on disk, in dependency-respecting parallel batches, without
invoking any LLM. The dispatcher is the executable face of the validator — what
F1.4 says is dispatchable, F1.5 actually dispatches (in stub mode).

The F1.5 stub is a self-test rig, not the production orchestrator. Real LLM
execution lands in a later phase; the dispatch surface here is shaped so the
real `delegate_task` can be swapped in by replacing `scripts/run_specialist.py`
without touching `scripts/dispatch.py`.

## Scope

Include:
- `scripts/run_specialist.py` — single-specialist stub runner. CLI:
  `python3 scripts/run_specialist.py <specialist_id> <role> <json_payload>`
  where `json_payload` is `{task, context, output_schema}`. It writes a
  deterministic JSON file to `logs/specialists/<id>.<n>.json` and prints
  `<id>: ok` to stdout. Exit 0 on success, 1 on bad input. NO LLM call.
- `scripts/dispatch.py` — batch dispatcher. CLI:
  `python3 scripts/dispatch.py PLAN.json [--max-parallel N] [--fail-mode
  {raise,continue,simulate:N}] [--self-test]`. Reads the plan, calls
  `validate()` from `scripts/validate_plan` (importable, F1.4 contract), and
  for each batch fans out `subprocess.run([sys.executable,
  "scripts/run_specialist.py", ...])` calls in parallel via
  `concurrent.futures.ThreadPoolExecutor`. Aggregates per-specialist outputs
  into `logs/orchestration-trace.jsonl` (one JSON object per line: ts, batch
  index, specialist id, role, status, output_path, elapsed_ms). Exit codes: 0
  if every specialist ran (success OR recorded-as-failed), 1 if the plan is
  invalid (re-validate first), 2 on usage / IO / unexpected dispatcher error.
- `--self-test`: end-to-end against a known plan fixture; asserts (a) every
  specialist file exists, (b) trace has exactly N lines, (c) batches ran in
  declared order (recorded batch index ascending per specialist), (d) no
  simultaneous overlap of dependent specialists (the `wr` specialist with
  dependency on `r1` must run in a later batch).
- SKILL.md §4 Batch paragraph: ONE appended clause `Run scripts/dispatch.py
  PLAN.json (exit 0 = every specialist ran, trace in logs/orchestration-trace.jsonl).`
- `README.md` status table: F1.5 → In progress.

Exclude (for now):
- Real LLM execution / `delegate_task` calls. The stub only writes files.
- Recovery / retry (F1.7). Synthesis (F1.6). Log writer beyond the trace
  (F1.8). No Python deps. No profile installation.

## Spec section

### `run_specialist.py`

```text
usage: run_specialist.py [-h] specialist_id role json_payload
```

- Reads `json_payload` from argv (so dispatch can shell-escape), validates it
  has `task` (str), `context` (str), `output_schema` (object). Bad input → exit 1
  with `error: ...` line.
- Writes a deterministic file:
  - Path: `logs/specialists/<id>.<n>.json` where `<n>` is a per-run counter
    found by scanning the directory for the highest existing `<id>.\d+.json`
    and adding 1 (so a re-run doesn't clobber, F1.7-friendly).
  - Content: `{"id": ..., "role": ..., "task": ..., "context": ...,
    "output_schema": ..., "timestamp": ISO-8601 UTC, "stub": true}`. Schema
    content is passed through unvalidated (F1.6).
- Prints `<id>: ok` to stdout on success.
- Exit 0 on success, 1 on bad input, 2 on IO.

### `dispatch.py`

```text
usage: dispatch.py [-h] [--max-parallel N] [--fail-mode MODE] [--self-test] PLAN.json
```

- Re-validates the plan via `validate_plan.validate(plan)`. Any errors → print
  them, exit 1. Warnings → print, continue.
- Creates `logs/specialists/` if missing.
- Honors dependency edges: compute `idpos = {id: i for i, sp in specialists
  enumerate}` and `batch_of = {id: i for i, batch in enumerate(batches) for
  sp_idx in batch}`; verify a dependency only crosses later batches (validator
  already enforces, but dispatcher re-checks defensively — exit 1 if violated).
- For each batch index in order:
  - Build a `ThreadPoolExecutor(max_workers=min(N, len(batch)))`.
  - For each specialist index in batch, build `argv = [sys.executable,
    "scripts/run_specialist.py", specialist_id, role, json.dumps(payload)]`
    and submit; record start ts.
  - As futures complete, record end ts, status, output path. On nonzero exit
    under `--fail-mode continue`, record `status: failed` and continue; under
    `raise` (default), cancel remaining futures in this batch and exit 1.
  - `--fail-mode simulate:N` (deterministic self-test mode): make the Nth
    specialist in each batch fail once, recording it as `failed`, then
    continue. Used by `--self-test` only.
- Writes `logs/orchestration-trace.jsonl` AFTER all batches complete (one
  file write at the end, not per-line, to keep the stub race-free).
- Stdout summary: `dispatch: <N> specialists, <B> batches, <T> failed`.
- Exit 0 if every specialist ran (success OR recorded-as-failed); exit 1 if
  the plan is invalid or `--fail-mode raise` triggered; exit 2 on usage/IO.

## Implementation notes

- Decision D9 (controller-locked): stub `run_specialist.py` writes files
  deterministically — no network, no LLM. Phase 1 acceptance is "structure is
  right", not "AI produced an answer". Real LLM integration is out of scope.
- Decision D10: import `validate_plan.validate` rather than re-parsing. F1.4
  shipped that function as importable; use it.
- Gotcha: thread pool workers must `subprocess.run` (not call the function
  in-process) so a future real `run_specialist.py` can be a separate process
  boundary. The stub is the same shape — already a separate process.
- Gotcha: `batch_of` is integer→integer. Use it for dep order, not specialist
  index.
- Reference: `references/orchestrator.md` §§2–3 (schema, index-vs-id),
  PRD R3/R4/R5/R15.
