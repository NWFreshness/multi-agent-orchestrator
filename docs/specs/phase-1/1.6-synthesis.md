# Feature 1.6: Synthesis contract (`references/synthesis.md`)

**Phase:** 1 — MVP, fixed models
**Status:** completed
**Estimated effort:** half-day wall (subagent implement + two-stage review; spec-only feature like F1.2/F1.3)
**Depends on:** 1.5
**Blocks:** 1.7, 1.8

## Goal

The synthesis contract: how specialist outputs are merged into one final answer,
in what shape, with what gap-flagging rules. Captures the carry-forward from
F1.1 (quality minor 3) and gives F1.7 (recovery) and F1.8 (log writer) a stable
target.

## Scope

Include:
- `references/synthesis.md` with these subsections, each concrete and
  testable:
  1. **Re-invocation pattern** — after dispatch, the parent re-invokes the
     Orchestrator with the aggregated specialist outputs. Confirms
     `references/orchestrator.md` §6's actor model (no new conflict).
  2. **Synthesizer input shape** — exactly: `{task_summary, specialists: [{id,
     role, goal, output}], trace: <path or lines>, errors: [], warnings: []}`.
     `output` per specialist is the parsed JSON object the stub writes
     (F1.5's `logs/specialists/<id>.<n>.json`). If a specialist failed (status
     `failed` in the trace), `output` is `null` and the entry has
     `failure_reason`.
  3. **Output JSON schema** — the final synthesized answer. The four
     canonical fields below are LOCKED (referenced by F1.8's log writer and
     F1.10's tests):

     ```json
     {
       "answer": "<markdown or plain text — the synthesized result>",
       "key_points": ["<bullet>", "..."],
       "confidence": "high|medium|low",
       "gaps": ["<fact or perspective the synthesis could not confirm>"]
     }
     ```

     `answer` is always non-empty. `key_points` is a list of 0+ short strings.
     `confidence` is one of the three literals — never null. `gaps` lists
     things the synthesis could not confirm (failed specialists, missing
     citations, dissent); it is allowed to be empty. Optional: `sources`
     (list of URLs / file paths cited) and `failed_specialists` (list of
     specialist ids that failed, even if `gaps` already covers it). Do not
     require them in v0.1; mention them as future additions.
  4. **Gap-flagging rules** — locked list, in priority order: (a) every
     specialist in `failed_specialists` MUST appear in `gaps`; (b)
     contradictions between specialists' `output` are surfaced in `gaps` with
     both sides quoted; (c) any specialist whose `output` is null for a
     non-failure reason (e.g. file unreadable) MUST appear in `gaps`; (d)
     low-citation claims (any claim without a `sources` entry from a
     researcher/reviewer specialist) MAY appear in `gaps` as a soft flag.
  5. **Confidence rubric** — `high` when no `gaps` and no failed
     specialists; `medium` when 1–2 `gaps` and zero failed specialists;
     `low` when any failed specialist OR more than 2 `gaps`. Document this
     as the default; the Orchestrator may override with reasoning (one
     sentence) appended to the synthesized answer.
  6. **What the synthesizer is NOT** — explicit out-of-scope: it does not
     dispatch (parent does); it does not retry (F1.7 does); it does not
     write the orchestration log file (F1.8 does); it does not validate the
     plan (F1.4 does). Pointer to each.
- `SKILL.md` §4 Synthesize paragraph: ONE appended clause
  `The synthesis contract and output schema are defined in references/synthesis.md.`
- `README.md` status table: F1.6 → In progress.

Exclude (for now):
- The actual synthesizer implementation (Python or otherwise). F1.6 is the
  contract only — the executor arrives in F1.7/F1.10 or beyond.
- The `sources` and `failed_specialists` optional fields (mentioned as
  future, NOT required).
- JSON Schema for the output (a textual description is enough for F1.6; a

- No Python/scripts; no validator code; no dispatcher changes.

## Spec section

Locked output example (must parse as JSON, must have the four canonical
fields, must satisfy the gap rules above):

```json
{
  "answer": "Synthesized result text the user actually reads.",
  "key_points": ["First concise finding.", "Second concise finding."],
  "confidence": "high",
  "gaps": []
}
```

Low-confidence example (one failed specialist forces low + a gap):

```json
{
  "answer": "Best-effort result; the benchmark numbers are not included.",
  "key_points": ["Recommendation: postgres.js."],
  "confidence": "low",
  "gaps": ["bench-runner specialist failed; benchmark numbers missing."]
}
```

Confidence rubric (locked):

| Condition | Confidence |
| --- | --- |
| 0 gaps, 0 failed | high |
| 1–2 gaps, 0 failed | medium |
| >2 gaps, 0 failed | low |
| any failed specialist | low |

## Implementation notes

- Decision D11 (controller-locked): four canonical fields — answer,
  key_points, confidence, gaps. Optional fields (sources, failed_specialists)
  are NOT required. F1.6 is the contract; F1.10 may add a JSON Schema.
- Decision D12: confidence is a literal enum (high/medium/low), never null
  and never a number. The Orchestrator may override with one sentence
  appended to `answer`.
- Gotcha: gap rule (a) and confidence rule "any failed specialist → low"
  together mean a single failed specialist forces BOTH a gap entry AND
  low confidence. Document this clearly so F1.7 doesn't re-litigate.
- Reference: PRD §§6 (R7, R8), 8; `references/orchestrator.md` §6
  (re-invocation model, lock the actor); `references/archetypes.md` §3
  (output_schema deferral now closes here); F1.5 stub output shape.
