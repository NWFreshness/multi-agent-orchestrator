# Feature 1.10: Test driver (last feature before Phase 1 MVP)

**Phase:** 1 — MVP, fixed models
**Status:** in_progress
**Estimated effort:** short (half-day wall including review; tiny code)
**Depends on:** 1.1–1.9
**Blocks:** nothing (this is the last feature)

## Goal

A single stdlib-only CLI `scripts/run_tests.py` that runs every existing
per-script `--self-test` and reports one combined pass/fail, so the user
has a single command to verify the whole Phase 1 surface. No new test
code; the per-script self-tests are the test surface. Rigor comes in Phase 2.

## Scope

Include:
- `scripts/run_tests.py` (new, stdlib-only).
  - Discovers each testable script by scanning `scripts/` for files ending
    in `.py` and *not* starting with `_` (skip `__init__.py` etc.). For
    each, runs `python3 scripts/<name>.py --self-test` as a subprocess
    and captures the output + exit code.
  - Test order is locked (so a user running it twice gets a stable output):
    `validate_plan.py`, `dispatch.py`, `write_log.py`. (F1.9's slash
    command has no --self-test by design and is excluded.)
  - Output: a markdown table per suite, with columns `suite | expected |
    passed | status`. Expected counts are hard-coded (the implementer MUST
    not grep the per-script output to compute the expected number —
    hard-coding the contract is the whole point of the driver):
    - `validate_plan.py` → 15 passed
    - `dispatch.py` → 7 passed
    - `write_log.py` → 7 passed
  - Final line: `TOTAL: 29/29 passed` (or the actual sum) + `STATUS: green`
    or `STATUS: red` (one or more failed).
  - Exit code: 0 if every suite passed; 1 if any failed; 2 on usage/IO
    (e.g. a script not found, or a per-script self-test crashing in a
    way the wrapper can't classify).
  - CLI: `python3 scripts/run_tests.py [--self-test]` (the latter just
    runs the validate_plan self-test as a smoke check; the default runs
    all three).
- `README.md`: phase status table updated (Phase 1 → Done; F1.10 row →
  Done). One line of phase-1-done narrative above the table.
- `docs/specs/phase-1/1.10-tests.md` Status → completed.

Exclude (for now):
- A real `tests/` directory with `unittest.TestCase` per module. The PRD
  promised this would be added in a later phase; F1.10 is intentionally
  a thin driver only. (The per-script --self-tests already cover the
  regression surface; what F1.10 adds is a single command and a stable
  contract on the count.)
- Mocking of subprocess (the driver shells out to per-script self-tests;
  we do not re-implement them in-process).
- New scripts; the per-script --self-test surfaces are FROZEN — do NOT
  modify any other script in this PR.

## Spec section

CLI:
- `python3 scripts/run_tests.py` → run all three suites, print table, exit 0/1.
- `python3 scripts/run_tests.py --self-test` → run the validate_plan self-test
  only (sanity check the driver itself; prove the driver can find + invoke
  a self-test correctly). Exits 0 if it finds and runs validate_plan, 1 if
  it doesn't, 2 on IO.

Stdlib only. Imports: argparse, subprocess, sys at most.

Hard-coded expectations (locked):
- `validate_plan.py --self-test` → "15/15 passed" in stdout
- `dispatch.py --self-test` → "7/7 passed" in stdout
- `write_log.py --self-test` → "7/7 passed" in stdout

Match strategy: grep the per-script stdout for the exact pattern
`<N>/<N> passed`. (If the implementer wants to be slightly more robust,
match `<N>/<N>` followed by `passed` on the same line.) Do NOT re-run
the self-test under different conditions; do NOT recompute the expected
count from anything dynamic.

If a per-script self-test is missing its expected line, the driver reports
that suite as red (exit 1) even if the subprocess returned 0. This guards
against a per-script implementer changing the count string without
updating the driver.

## Implementation notes

- Decision D18 (controller-locked): the expected counts are hard-coded,
  not computed. The whole point of F1.10 is to lock the contract: a
  per-script implementer who silently changes `15/15` to `16/16` should
  break the driver. The driver is a tripwire, not a discovery mechanism.
- Decision D19: discovery is by scanning `scripts/*.py` (excluding any
  starting with `_`), but execution order is LOCKED to the order above.
  Hard-coding the order keeps the user's experience deterministic; if a
  future test gets added, both the order and the expected count must be
  updated together.
- Gotcha: per-script self-tests need to be run with `python3` (the same
  interpreter that ran the driver), not `sys.executable` of a different
  version. Use `sys.executable` to be safe across environments.
- Gotcha: capture stdout AND stderr from each per-script subprocess. A
  per-script self-test that crashes to stderr (a traceback) should still
  be classified as a failure, not as "passed because exit was 0 by
  accident" (this matches the F1.4 C1 / F1.5 IndexError lessons).
- Reference: F1.4 spec §"Spec section" (the original --self-test pattern);
  F1.5 spec §"--self-test"; F1.7 spec §"--self-test extension"; F1.8 spec
  §"--self-test". This is the unifying layer.
