# Feature 1.7: Error recovery (retry-once + gap flagging)

**Phase:** 1 — MVP, fixed models
**Status:** in_progress
**Estimated effort:** half-day wall (subagent implement + two-stage review)
**Depends on:** 1.5, 1.6
**Blocks:** 1.9

## Goal

The dispatcher retries each failed specialist exactly once (the PRD R8 contract)
and records retry outcomes on the trace, so the synthesis step (F1.6) has the
information it needs to populate `gaps` and `confidence`. First code feature
that actually extends `scripts/dispatch.py`.

## Scope

Include:
- **Extension to `scripts/dispatch.py`** (no new files):
  - New CLI flags: `--max-retries N` (default 1) and `--retry-strategy
    {restart,continue}` (default `continue`). `N=0` disables retry entirely.
  - Per-specialist retry: any specialist whose first run returned `status:
    failed` is retried up to `max_retries` additional times. Each retry is a
    fresh `subprocess.run` with the same argv. Record every run as a separate
    trace line (not aggregated) so F1.6 / F1.8 can see retry history.
  - Final per-specialist status logic: if ANY run succeeded → `status: ok`
    (record a `retries: <k>` field noting how many attempts were needed); if
    ALL runs failed → `status: failed` (record `retries: <N+1>` and the last
    `error`).
  - `--retry-strategy restart` re-runs the whole batch on any failure (N
    retry slots, each one restarts the failing batch). `continue` retries
    only the failing specialist in place. Both still respect `--max-retries`.
  - Exit code unchanged from F1.5: 0 if every specialist ended `ok` OR
    `failed-with-retries-exhausted`; 1 only on invalid plan / raise mode; 2
    on usage/IO.
- **`--self-test` extension** (extend F1.5's, don't replace):
  - Existing 4 self-test cases must still pass (regression).
  - New cases (additive): retry-once-then-ok (specialist fails first
    attempt, succeeds second; final status `ok` with `retries: 1`),
    retry-exhausted (specialist fails both attempts; final `failed` with
    `retries: 2` and last error preserved), retry-disabled (--max-retries
    0 keeps F1.5 behavior; 0/0 means `retries: 0`).
- **`--self-test --max-retries 0` regression**: must still print 4/4 + 1/1
  (or similar) to keep F1.5's behavior.
- **F1.6 integration note** (in `--help` and a code comment, NOT a separate
  file): the trace's `status: failed` entries are the inputs F1.6's
  synthesizer uses to populate `failed_specialists` and `gaps`. The
  dispatcher does not synthesize — it just records faithfully.
- `SKILL.md` §4 Recover paragraph: ONE appended clause `Run scripts/dispatch.py
  PLAN.json (default retries each failed specialist once before recording
  status: failed).`
- `README.md` status table: F1.7 → In progress.

Exclude (for now):
- Real LLM-driven retry with a different prompt (F1.7 is the dispatcher, not

## Spec section

Trace line extensions (additive, do NOT break F1.5's existing keys):

```json
{"ts": "...", "started_ts": "...", "batch": 0, "id": "r1", "role": "researcher",
 "status": "ok", "output_path": "logs/specialists/r1.2.json",
 "elapsed_ms": 142, "returncode": 0, "retries": 1}
```

`retries` is the count of ADDITIONAL attempts after the first one. A
specialist that never failed has `retries: 0`. A specialist that failed
twice and succeeded on the third has `retries: 2`. `error` (if present)
records the LAST failure.

CLI flag defaults are LOCKED: `--max-retries 1`, `--retry-strategy continue`.
Both are integer / choice validated by argparse. `--max-retries 0` is
allowed and means "no retry, F1.5 behavior".

## Implementation notes

- Decision D13 (controller-locked): `--max-retries 1` is the spec default
  (PRD R8 says "1 retry"). Setting it lower disables retry; setting it
  higher is allowed but not recommended.
- Decision D14: each retry attempt is a SEPARATE trace line (not aggregated).
  Reason: F1.6 / F1.8 can see the full history without losing detail.
- Gotcha: `--max-retries 0` must keep F1.5's behavior byte-for-byte. The
  implementer should structure retry as a no-op when N=0, not skip the loop
  body via a special case.
- Gotcha: the stub `run_specialist.py` succeeds deterministically. To test
  retry-once-then-ok, the dispatcher must force a deterministic failure on
  the FIRST attempt only (e.g. by writing a `failure_injection` env var the
  stub honors). The retry succeeds because the injection clears. This is
  test-rig-only, never affects the real stub.
- Gotcha: `--fail-mode continue` records the failure but does NOT raise —
  retry must still be applied. The F1.5 spec said "raise cancels remaining
  in batch and exits 1"; F1.7 says "raise also cancels remaining retries".
  Test the interaction.
- Reference: PRD R8 (retry-once with adjusted prompt — the dispatcher
  re-runs the same argv, prompt adjustment is the Orchestrator's job),
  references/synthesis.md §4 (gap rule (a) — every failed specialist MUST
  surface in `gaps`).
