# Feature 3.1: Persistent specialist pools (named experts)

**Phase:** 3 — Advanced
**Status:** in_progress (spec author running)
**Estimated effort:** half-day wall
**Depends on:** nothing (first Phase 3 feature)
**Blocks:** nothing (pool wiring into plans deferred past F3.1)

## Goal

Define the persistent specialist pool contract: named sets of specialist
entries stored as JSON in the skill repo so a recurring team (e.g.
researcher + critic + writer) survives across sessions and the
Orchestrator can copy/adapt it instead of rebuilding it every run.
F3.1 ships the contract + one example pool. No validator/dispatcher
changes — pools are advisory in F3.1.

## Scope

Include:
- **`references/pools.md`** (new): pool contract doc. Defines:
  - Location: `pools/<name>.json` in the skill repo (D38). Repo-local
    files survive across sessions; users add their own pool files in
    the same dir.
  - Naming: `<name>` is lowercase alphanumeric + dashes, matches the
    filename stem (`my-pool` ↔ `pools/my-pool.json`).
  - File shape: `{"name": str, "description": str, "members": [...]}`.
  - Member shape: EXACTLY the F1.2 specialist 7-field entries (D39) —
    `id, role, goal, context, output_schema, tools, model`, all
    concrete strings (no `{placeholders}` or templates in F3.1; D40).
    Member `role` values must exist in `references/archetypes.md`.
  - Advisory use (D40): the Orchestrator copies/adapts members into a
    plan's `specialists[]` (re-pointing ids, batches, dependencies per
    task). The plan JSON gains NO new key in F3.1; validator and
    dispatcher are untouched.
- **`pools/research-trio.json`** (new example): `researcher` + `critic`
  + `writer` for a recurring topic-brief task, all 7 fields concrete.
  Three members keeps the example above the F1.4 3-specialist floor and
  satisfies the reviewer/critic rule.
- `SKILL.md` §8 References Index: ONE appended bullet
  ``- `references/pools.md` — persistent specialist pool contract + `pools/` examples (defined in F3.1).``
- `README.md` status table only: Phase 2 → Done, F2.6 → Done, add
  `F3.1 | Persistent specialist pools (named experts) | In progress`,
  Phase 3 row → In progress.
- `docs/specs/phase-3/3.1-specialist-pools.md`: Status → completed.

## Exclude (for now)

- Validator/dispatcher support for pools (no `pool` key in plan JSON;
  no `scripts/` changes at all in F3.1).
- Template placeholders (`{task}`, variable substitution) — D40 locks
  concrete strings; templates are a later feature if ever.
- `~/.hermes` pool discovery (that pattern belongs to F3.2 custom
  archetypes; F3.1 is repo-local only).
- Cache integration (F3.3), streaming (F3.4), background mode (F3.5).
- `.gitignore` changes for user pools (no user pools ship in F3.1).

## Locked behavior

- Decision D38 (controller-locked): pools live in skill-repo
  `pools/<name>.json`. Rationale: portable with the skill, survives
  across sessions via git, zero new config plumbing. Per-profile
  `~/.hermes` discovery is F3.2's pattern, not F3.1's.
- Decision D39: member entries reuse the F1.2 7-field specialist shape
  verbatim. No new schema to learn, no validator change needed, and
  any pool member can be pasted into a plan as-is.
- Decision D40: F3.1 pools are ADVISORY + CONCRETE. The Orchestrator
  copies members and adapts goal/context per task; nothing resolves
  pools automatically. Automatic pool expansion (if ever) is a later
  feature, not this one.
- Gotcha: member `id` values only need uniqueness WITHIN the pool
  file; the Orchestrator re-points ids when composing a plan.
- Gotcha: `output_schema` in the example must be a real JSON Schema
  object (`{"type": "object"}` minimum), not a string — F1.2 §2 shows
  it as a string in the pretty-printed example but F2.4 enforces
  object content. Follow the F2.4 form.
- Reference: PRD R16 (pools), PRD §9 Phase 3 list; F1.2 plan schema;
  F1.3 archetype names; F2.1/F2.2 docs-only precedent.
