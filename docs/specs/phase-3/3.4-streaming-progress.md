# Feature 3.4: Streaming progress to a file sink

**Phase:** 3 — Advanced
**Status:** completed
**Estimated effort:** half-day wall
**Depends on:** nothing (independent surface; builds in listed order after 3.3)
**Blocks:** nothing

## Goal

PRD R18 (file half): while a dispatch runs, progress streams out —
one JSON line per completed specialist record, appended per batch to a
`--progress PATH` sink a consumer can `tail -f`. Telegram/Slack
delivery stays out of the skill: Hermes' own `deliver` targets consume
the file downstream (different layer, not reinvented here).

## Scope

Include:
- **`scripts/dispatch.py`**:
  - Flag `--progress PATH` (default None = disabled; order-independent).
  - Thread `progress_path: Optional[str] = None` kwarg through
    `dispatch_plan` (same threading shape as F2.6 `tokens_per_char` /
    F3.3 cache kwargs — extend the same call chain, no new plumbing
    pattern).
  - After EACH batch's harvest completes, append that batch's records
    to the sink: one `json.dumps(record, sort_keys=True)` line per
    record, file opened in append mode, created with parent dirs if
    needed (D49). The lines are the trace-record dicts verbatim (D52)
    — no new serialization shape to learn; a consumer replays the
    trace incrementally.
  - Appends happen BEFORE the F2.4 schema check / F2.6 token stamp
    passes (records stream in harvest form; the final trace file
    remains the enriched source of truth). Order within a batch =
    harvest order (completion order, not plan order — it is a stream).
  - Best-effort, never blocks (D51): any IO failure → single
    `WARNING: progress sink ...` to stderr, dispatch continues, exit
    code unaffected. `--dry-run` never touches the sink (nothing
    dispatched). Disabled path (`None`) touches nothing — zero
    behavior change for existing users.
  - `--self-test` +2 fixtures (17→19): STREAM (2-batch plan +
    temp sink → line count == record count, every line parses as JSON
    with `id`/`batch`/`status`, batch-0 lines precede batch-1 lines)
    and SILENT (no flag → no file created at the would-be path).
- **`references/streaming.md`** (new, short): sink contract (D49 file
  sink + line shape = trace record), consumer recipe (`tail -f`,
  `json.loads` per line), layer rule (D50: Telegram/Slack via Hermes

- **`scripts/run_tests.py`**: dispatch 17→19. EXPECTED_TOTAL 51→53
  via existing `sum()`.
- `SKILL.md` §8: ONE appended bullet for `references/streaming.md`.

## Exclude (for now)

- Telegram/Slack/discord delivery from skill scripts (D50 — Hermes
  layer concern; the file is the handoff).
- Per-record (intra-batch) streaming — per-batch appends are the
  locked granularity (worker-thread appends need no new imports and
  add interleaving complexity for zero contract gain).
- `write_log.py` live-tail mode (the log is written post-run; F1.8
  contract holds).
- Retried intermediate attempts get their own lines (they are trace
  records like any other — no special-casing).

## Locked behavior

- Decision D49 (controller-locked): sink is a local append-only JSONL
  file at an explicit `--progress PATH`. Parent dirs auto-created.
  Rationale: the PRD's "(Telegram, log file)" gives the file channel
  explicitly; it needs no credentials, no network, no new deps.
- Decision D50: skill scripts NEVER speak Telegram/Slack. The handoff
  is the file; Hermes `deliver` targets (cronjob, gateway) consume it.
  Reuse, don't reinvent (PRD §1).
- Decision D51: sink IO NEVER fails a run. Miss/permission/readonly
  → one WARNING, continue. A progress sink that can abort a dispatch
  is worse than no sink.
- Decision D52: line shape = the trace-record dict verbatim
  (`json.dumps(record, sort_keys=True)`). No projection, no second
  schema — the consumer already understands trace records.
- Gotcha: append AFTER harvest per batch, INSIDE the batch loop —
  not at end of `dispatch_plan` (that would be a dump, not a stream).
  The `cancel_remaining` early-return path (fail_mode=raise) must
  still have streamed the batches that completed — appending inside
  the loop gives this for free.
- Gotcha: open-append-close per batch (not one handle for the run):
  a `tail -f` consumer sees flushed lines per batch, and a crashed
  run keeps everything through the last completed batch.
- Gotcha: self-test temp sink must live under `/tmp`
  (`_f34_progress_<pid>.jsonl`), removed in `finally`. Never default
  to a repo-relative path in tests.
- Reference: PRD R18; dispatch.py batch loop + `_harvest_with_retries`
  return shape; F2.6/F3.3 kwarg-threading precedent.
